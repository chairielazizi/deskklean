# DeskKlean v1.1.0 — Release Plan

**Status:** 🔜 specified, not built
**Baseline:** v1.0.1 (released 2026-10-26, tag `v1.0.1` → `e49c54b`)
**Branch:** `v1.1.0-work`
**Classification:** **minor** — new backward-compatible capabilities. No settings-schema change, no IPC contract removal, no new destructive scope.

---

## 1. Why this release exists

`docs/PLANNED-RELEASE-ANALYSIS.md` §3 identified a class of defect that is worse than a missing
feature: **settings and UI that promise work the backend never performs.**

- `AppSettings.autoCheckUpdates` is persisted and rendered as a toggle, but no updater exists.
- `AppSettings.customRules` is persisted, has a full add/remove UI, and is **never read by `src/main`**.
- `AppSettings.scheduledCleanEnabled` / `scheduledCleanFrequency` are persisted and rendered, with no
  Task Scheduler integration and no IPC handler.
- `InstalledApp.leftoversDetected` is `null` for every app because no scan exists — correct after
  v1.0.1 (it used to lie with `0`), but the feature the UI implies still does not exist.

Every one of these is the same failure the project exists to eliminate: a control that implies a
capability. v1.1.0 closes all four. That is the whole release.

### Non-goals (explicitly out)

- Firmware-level Secure Erase (ATA / NVMe Format) — v2.
- Browser privacy-data cleaning (caches, cookies, history, sessions) — v2.
- RegistryFixer file-association category — held until OQ-1 (`UserChoice` hash) is verified.
- Browser extension toggle/remove — D-R2-7 stands; deliberately absent.
- i18n, light mode, settings-schema migration — v2.
- Any change to `AppSettings` shape. v1.0.x `settings.json` must load unmodified.

## 3. Build order and why

1. **Phase 16 (updater)** — first, because it is the only phase that changes packaging and CI. If
   `latest.yml` / `.blockmap` generation or the release-asset list is wrong, every later phase
   inherits a broken pipeline. Land it while the surface is small.
2. **Phase 17 (custom rules)** — pure additive scan/plan work on an existing framework. Low risk,
   and it validates that `createSmartCleanPlan` can be extended without breaking Phase 6.
3. **Phase 18 (scheduled clean)** — depends on Phase 17 only in that both consume SmartClean; it
   needs the headless entry point, which touches `main.ts` lifecycle.
4. **Phase 19 (leftovers)** — most heuristic, so it goes last, and it ships detection-only. The
   cleanup path reuses the framework; no new destructive primitive.

One release (`v1.1.0`) at the end. No per-phase tags — the versioning rule (D-R2-8) reserves minor
for a capability landing, and this release is four capabilities delivered together.

## 4. Invariants every phase must hold

These are the project's existing rails, restated because all four phases touch them:

| Rail | Meaning here |
|---|---|
| **Never invent a value** | A failed update check is `error`, not "up to date". A rule whose root is missing is `failed`, not 0 bytes. A detection failure is `null`, not `0`. A task that is not registered is `null`, not "next run: never". |
| **Verify by read-back** | Update install only after `downloaded`. Task registration confirmed by re-querying Task Scheduler. Leftover deletion confirmed by re-stat. |
| **Back up before destroying** | Registry leftovers get a `.reg` backup through the existing framework. Custom-rule and leftover file deletions route to the Recycle Bin (user data, D-R2-4). |
| **Fail closed** | A scheduled run that cannot determine elevation reports which categories it skipped. A portable build refuses to register a scheduled task instead of registering a path that will vanish. |
| **Unverified paths don't ship** | Custom rules are user-supplied, so they are validated per run against the protected list; nothing about them is assumed safe. |
| **Partial failure is reported as partial** | `completed` / `failed` / `skipped` stay separate in every result. |

## 5. Verification bar (unchanged from ROADMAP §7)

| Layer | Who | What |
|---|---|---|
| Pure logic | Automated, Linux | New suites: `test-updater.mjs`, `test-custom-rules.mjs`, `test-scheduled-clean.mjs`, `test-leftovers.mjs`. Wired into the existing `for f in scripts/test-*.mjs` loop in `.github/workflows/ci.yml`. |
| Types | Automated | Both `tsc` configs clean (`tsconfig.main.json`, `tsconfig.json`). |
| Behaviour on Windows | Owner | Per-phase acceptance script, written into each phase doc. |
| Destructive round-trip | Owner | Leftover cleanup: delete → confirm gone → restore from Recycle Bin → confirm back. |

**Nothing in this release can be executed on the build machine.** No Windows, no PowerShell, no
Task Scheduler, no registry. Every phase ships on read-and-reason plus pure-logic tests; the Windows
acceptance script is the owner's, and it is not optional.

## 6. Known environmental hazard (accepted, not fixed)

`.git` is **not** in the repo-root `.stignore`, so Syncthing replicates git internals between the
owner's Windows box and this Linux box. As of 2026-10-26 there are **79 `*sync-conflict*` files
inside `.git/objects`**, all reported as `bad sha1 file` by `git fsck`, plus conflict copies of
`FETCH_HEAD`. They are unreferenced garbage today, but two machines writing the same `.git`
concurrently is how a ref or the index gets lost.

Owner decision D-11-5: leave it for now. Consequence for this release: **before every push, run
`git fetch && git status -sb` and reconcile with `origin/main`.** If the Windows box and this box
ever commit at the same moment, stop and resolve by hand rather than force-pushing.

## 7. Definition of done for v1.1.0

1. All four phases implemented by the implementing agent (agy), each verified against its own
   acceptance script on Windows.
2. All pure-logic suites green on CI, `tsc` clean on both configs.
3. `AppSettings` unchanged; a v1.0.1 `settings.json` loads and behaves identically.
4. `docs/RELEASE-NOTES.md` gains a `# DeskKlean v1.1.0` section at the top.
5. `README.md` download block points at v1.1.0.
6. CI on tag `v1.1.0` produces `DeskKlean Setup 1.1.0.exe`, `DeskKlean-Portable-1.1.0.exe`,
   `latest.yml`, and `.blockmap` files, and publishes them as release assets.
7. Auto-update from an installed 1.0.1 to 1.1.0 works end to end on the owner's machine.
