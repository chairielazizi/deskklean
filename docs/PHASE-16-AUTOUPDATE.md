# Phase 16 — Auto-Update Backend (stable channel)

**Status:** 🔜 specified, not built
**Depends on:** Phase 15a/15b (CI + packaging) ✅ · v1.0.1 baseline
**Classification:** minor (new capability, no schema change)
**Design refs:** DESIGN-DECISIONS Q5 (electron-updater + GitHub Releases), Q18 (channels — beta deferred), Q9 (signing deferred)

---

## Goal

Make `AppSettings.autoCheckUpdates` mean something. Today it is a persisted boolean rendered as a
toggle in Settings → General (`Settings.tsx:183`) with **no runtime consumer anywhere in
`src/main`**. This phase adds a real updater and wires that toggle to it.

Stable channel only (D-11-3). No `updateChannel` field is added to `AppSettings` in 1.1.0.

## 1. Why this is not just "add electron-updater"

`electron-updater` is only half the work. It needs three things this repo does not currently have:

1. **Update metadata in the release.** `latest.yml` and `*.blockmap` must exist as release assets.
   `electron-builder.yml` currently sets `publish: null` deliberately — see the comment in that file:
   a string value is treated as a provider name and fails with
   `Cannot find module 'electron-publisher-never'`. With publishing disabled, electron-builder still
   writes `latest.yml` and blockmaps **only if a publish provider is configured**.
2. **Those files must be uploaded.** `.github/workflows/ci.yml` currently uploads
   `release/*.exe` and `release/*.zip` only.
3. **A main-process state machine.** Nothing in the app can represent "checking" vs "failed" today,
   and the honesty rule forbids conflating them.


`--publish never` keeps the existing division of labour: electron-builder produces artifacts and
metadata, the workflow publishes them via `softprops/action-gh-release`. Do **not** let
electron-builder upload — the workflow already owns release creation and reads
`body_path: docs/RELEASE-NOTES.md`.

### 2.3 `.github/workflows/ci.yml`

```yaml
files: |
  release/*.exe
  release/*.zip
```

the release after the first tagged run. Verify with

### 2.4 `latest.yml` currently in `release/`

The existing `release/latest.yml` declares `version: 1.0.0` and is a stale local artifact. It is
gitignored (`/release`) and must not be committed. It will be regenerated by the build.

## 3. Main process — `src/main/system/updater.ts` (new)

```ts
export type UpdaterState =
  | 'idle'          // nothing attempted yet
  | 'disabled'      // autoCheckUpdates is false and no manual check in flight
  | 'unavailable'   // dev build or portable build — cannot self-update
  | 'checking'
  | 'available'     // updateVersion is known and non-null
  | 'not-available' // a check COMPLETED and reported no newer version
  | 'downloading'
  | 'downloaded'    // ready to install
  | 'error';

export interface UpdaterStatus {
  state: UpdaterState;
  currentVersion: string;          // app.getVersion()
  availableVersion: string | null; // null unless state is available/downloading/downloaded
  releaseNotes: string | null;     // null when the feed has none — never synthesised
  progressPercent: number | null;  // real from electron-updater, null when unknown
  bytesPerSecond: number | null;
  lastCheckedAt: string | null;    // ISO, only after a check actually ran
  error: string | null;            // populated ONLY in state 'error'
}
```

Functions:

| Function | Contract |
|---|---|
| `initUpdater(deps)` | Configures `autoUpdater`, `autoDownload = false`, `autoInstallOnAppQuit = false`. Installs event listeners that mutate and broadcast status. Never throws at startup. |
| `getUpdaterStatus()` | Returns the current `UpdaterStatus`. Safe to call before init (returns `idle`). |
| `checkForUpdates()` | Resolves to `UpdaterStatus`. Sets `checking`, then `available` / `not-available` / `error`. |
| `downloadUpdate()` | Only legal from `available`. Resolves to `UpdaterStatus`. |
| `quitAndInstall()` | Only legal from `downloaded`. Calls `autoUpdater.quitAndInstall()`. |

### 3.1 Honesty rails (these are the point of the phase)

- **`not-available` requires a completed check.** If `autoUpdater.checkForUpdates()` rejects, times
  out, or the feed is unreachable, the state is `error` with the message. It is never
  `not-available`. A user must never be told "you're up to date" by a machine that did not ask.
- **`lastCheckedAt` is only set on a completed check**, success or failure — not on `checking`.
- **`availableVersion` is `null` unless a real version came back.** No placeholder, no "latest".
- **`progressPercent` is `null` when the feed does not report it.** Do not compute a fake ramp from
  elapsed time.
- **`releaseNotes` is passed through or `null`.** Never generated.
- **Portable builds cannot self-update.** Detect `process.env.PORTABLE_EXECUTABLE_FILE` (already
  handled elsewhere in `ipc.ts` for portable awareness) and return
  `state: 'unavailable'` with a message naming the portable limitation. Registering an updater
  against a temp-extraction path is a lie that fails on the next launch.
- **Dev builds are `unavailable`**, not `error`: `!app.isPackaged` means the check cannot be
  meaningful, and calling that an error trains the user to ignore errors.

### 3.2 Startup behaviour

After `app.whenReady()`, if `settings.autoCheckUpdates` is true and the build is packaged and not
portable, call `checkForUpdates()` once, delayed (recommend 10 s after first window show) so it does
not compete with the initial CIM queries. Failure is silent to the user but recorded in the status
and the activity log — never a modal at startup.

## 4. IPC

Add to `IPC_CHANNELS` in `src/shared/constants.ts` (additive, no removals):

```ts
// Updater
UPDATER_GET_STATUS: 'updater:getStatus',
UPDATER_CHECK: 'updater:check',
UPDATER_DOWNLOAD: 'updater:download',
UPDATER_INSTALL: 'updater:install',
UPDATER_STATUS: 'updater:status',   // main -> renderer event
```

Handlers in `src/main/ipc.ts`, following the existing `ipcMain.handle` pattern. Broadcast
`UPDATER_STATUS` on every state transition via the `mainWindow.webContents.send` path already used
by `DISK_SCAN_PROGRESS`.

### 4.1 Three-layer wiring — the spec review found this was missing

A new IPC channel alone reaches nothing. Every existing feature crosses **four** layers, and the
updater must do the same or the renderer cannot call it:

| Layer | File | What to add |
|---|---|---|
| Channel constants | `src/shared/constants.ts` (`IPC_CHANNELS`, `:7-80`) | the five updater channels |
| API type | `src/shared/types.ts` (`DeskKleanAPI`, around `:669` where `uninstallApp` lives) | `getUpdaterStatus`, `checkForUpdates`, `downloadUpdate`, `installUpdate`, `onUpdaterStatus` |
| Preload bridge | `src/preload/index.ts` (`:93-116` shows the invoke/`ipcRenderer.on` pattern) | matching `invoke` calls + the event subscription/removal pair, mirroring `onDiskScanProgress` |
| Renderer client | `src/renderer/apiClient.ts` (`:991-994` selects `window.deskKleanAPI` or `mockAPI`) | passthrough methods **and** a `mockAPI` entry |

The `mockAPI` entry must be honest too: in browser preview it should report
`state: 'unavailable'` with a reason, not a fabricated "up to date". `apiClient.ts` already carries
invented preview data elsewhere (`:970` `spaceFreedBytes: 3420000000`, `:985`
`'Disabled 3 high-impact background updaters (-2.4s boot time)'`) — do not add a third fiction here.
Cleaning up those existing preview mocks is **out of scope** for Phase 16; note it for v2.

### 4.2 Settings are saved explicitly, not live

`Settings.tsx` mutates local React state via `updateSetting()` and persists only on the **Save
Settings** button (`handleSave` → `api.saveSettings`). Therefore:

- The updater must read `settings.json` from disk **at the moment it checks**, not cache the value at
  startup. Otherwise a user who enables the toggle and forgets to save gets silent no-ops, and a user
  who disables it and forgets to save gets an unexpected network call.
- Alternatively subscribe to `SETTINGS_SAVE` and refresh the cached flag. Either is acceptable; the
  spec requires that **the toggle takes effect only after Save**, and that the UI does not imply
  otherwise (no "enabled" toast before the write lands).

## 5. Renderer

- **Settings → Behavior card**: the existing `autoCheckUpdates` toggle (`Settings.tsx:183`, inside the
  Behavior card at `:175-215`) now drives real behaviour. Keep its label honest: *"Check for updates
  automatically"*.
- **Settings → new "Updates" card.** Correction from spec review: `Settings.tsx` has **no tabs today**
  — it is a single scrolling page of five cards (Appearance `:131`, Behavior `:175`, Scheduled
  Cleaning `:217`, Custom Clean Rules `:261`, Security `:307`), 329 lines total. Q13d's tabbed surface
  is an aspiration, not an existing structure, so this phase must **not** invent a tab system. Add an
  Updates card in the same `motion.div` card pattern as its neighbours. It shows:
  - current version (`APP_VERSION`)
  - state line: one of *"Not checked yet"*, *"Checking…"*, *"Update 1.1.0 available"*,
    *"Up to date (checked <time>)"*, *"Update check failed: <message>"*, *"Portable build — download
    the new version manually"*
  - **Check now** button (disabled while `checking`)
  - **Download** button when `available`; **Install and restart** when `downloaded`
  - real progress bar only when `progressPercent !== null`
- No fake spinners with fixed durations. No "up to date" text when `state === 'error'`.

## 7. Windows acceptance script (owner)

1. Install `DeskKlean Setup 1.0.1.exe`.
2. Confirm Settings → Updates shows current version `1.0.1` and state *"Not checked yet"*.
3. Click **Check now** with the network disconnected → state must be
   *"Update check failed: …"*, **not** "up to date".
4. Reconnect, click **Check now** before v1.1.0 exists → *"Up to date (checked <time>)"* with a real
   timestamp.
5. After v1.1.0 is published, check again → *"Update 1.1.0 available"*; download; confirm progress is
   real; **Install and restart**; confirm the app relaunches as 1.1.0.
6. Run the **portable** 1.0.1 build → Settings → Updates must say the portable build cannot
   self-update, and no check is attempted.
